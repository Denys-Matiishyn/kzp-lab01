## 2. Мета роботи
Пройти повний шлях від створення репозиторію й налаштування інфраструктури до консольної програми, яку можна відтворювано зібрати й запустити на Windows, macOS та Ubuntu. У результаті програма читає записи про проживання в готелі з UTF-8 файла, перевіряє їх, відкидає хибні рядки з поясненням причини, обчислює показники та виводить звіт у консоль і текстовий файл. Збірка, тести, статичний аналіз і пакування виконуються через Maven Wrapper та автоматично запускаються в GitHub Actions.

## 3. Постановка задачі
Створити консольну програму для обробки записів про проживання гостей готелю.

**Формат запису (варіант 14):** `room:int; guest:String; nights:int; nightlyRate:double; category:String`.
У CSV-файлі поля розділено крапкою з комою, без позначок типу:

```text
room;guest;nights;nightlyRate;category
101;John Doe;3;150.00;Standard
```

**Чотири показники варіанта:**

| № | Показник | Як обчислюється |
| :-- | :-- | :-- |
| 1 | Кількість коректних записів | лічильник записів, що пройшли всі перевірки |
| 2 | Сумарна кількість ночей | сума `nights` коректних записів |
| 3 | Загальний виторг | сума `nights × nightlyRate` коректних записів |
| 4 | Найдовше проживання | максимальне значення `nights` серед коректних записів |

**Параметри командного рядка:** `--help`, `--version`, `--input FILE` (за замовчуванням `data/input.csv`), `--output FILE` (за замовчуванням `out/report.txt`).

## 4. Структура програми
* **Пакет:** `ua.lpnu.kzp`.
* **Файли:**
    * `Main.java` — клас із методом `main`: розбір аргументів командного рядка, читання файла, перевірка кожного рядка, обчислення показників і запис звіту; допоміжний метод `buildSummary` формує текст підсумків;
    * `MainTest.java` — модульні тести JUnit 5.
* **Допоміжні файли:** `data/input.csv` (приклад вхідних даних), `README.md`, `REPORT.md`, `.gitignore`, `pom.xml`, Maven Wrapper (`mvnw`, `mvnw.cmd`, `.mvn/wrapper/`), `.github/workflows/ci.yml`.

**Потік даних:** `data/input.csv` (UTF-8) → читання рядок за рядком → пропуск рядка заголовка → перевірка рядка → перетворення полів → оновлення показників → один текст підсумків (`buildSummary`) → консоль і файл звіту.

**Перевірки рядка (у порядку виконання):**
1. перший рядок файла, що містить слово `guest`, вважається заголовком і пропускається (лише перший рядок);
2. рядок не порожній;
3. рівно п'ять полів (`split(";", -1)` зберігає порожні поля);
4. поля `room`, `guest`, `category` не порожні;
5. `room` і `nights` — цілі числа, `nightlyRate` — число з крапкою (інакше `NumberFormatException` перехоплюється на рівні одного рядка);
6. `room > 0`, `nights > 0`, `nightlyRate > 0`, значення `nightlyRate` скінченне (не `NaN` і не `Infinity`).

Показники оновлюються лише після успішного проходження всіх перевірок, тому хибний рядок на результат не впливає. Для кожного пропущеного рядка виводиться його номер, причина й сам рядок.

**Робота з файлами й форматування.** Шляхи будуються через `Path`, читання й запис виконуються в явному UTF-8 (`Files.newBufferedReader`, `Files.writeString`). Перед записом звіту створюється батьківський каталог шляху `--output` (`Files.createDirectories`); якщо шлях не містить каталогу (наприклад, `report.txt`), `getParent()` повертає `null`, і створення пропускається. Дробові числа форматуються з двома знаками після крапки незалежно від локалі (`Locale.ROOT`), роздільник рядків у звіті залежить від ОС (`%n`).

**Фрагменти реалізації класу-сутності `Booking.java`:**

Конструктор класу виконує жорстку валідацію інваріантів перед ініціалізацією полів, що унеможливлює створення об'єкта з невалідними даними:

```java
public Booking(int room, String guest, int nights, double nightlyRate, String category) {
    if (room <= 0) {
        throw new IllegalArgumentException("Room number must be greater than 0");
    }
    this.guest = Objects.requireNonNull(guest, "Guest cannot be null");
    if (guest.isBlank()) {
        throw new IllegalArgumentException("Guest cannot be blank");
    }
    if (nights <= 0) {
        throw new IllegalArgumentException("Nights must be greater than 0");
    }
    if (nightlyRate <= 0.0 || Double.isNaN(nightlyRate) || Double.isInfinite(nightlyRate)) {
        throw new IllegalArgumentException("Invalid nightly rate");
    }
    this.category = Objects.requireNonNull(category, "Category cannot be null");
    if (category.isBlank()) {
        throw new IllegalArgumentException("Category cannot be blank");
    }
    this.room = room;
    this.nights = nights;
    this.nightlyRate = nightlyRate;
}
```
Фабричний метод `fromCsv` інкапсулює логіку розбору сирого рядка файлу, перевіряє кількість колонок та делегує створення об'єкта конструктору:

```java
public static Booking fromCsv(String line) {
    if (line == null) {
        throw new IllegalArgumentException("Line cannot be null");
    }
    String[] parts = line.split(";", -1);
    if (parts.length != 5) {
        throw new IllegalArgumentException("Expected 5 fields, got " + parts.length);
    }
    try {
        int room = Integer.parseInt(parts[0].trim());
        String guest = parts[1].trim();
        int nights = Integer.parseInt(parts[2].trim());
        double nightlyRate = Double.parseDouble(parts[3].trim());
        String category = parts[4].trim();
        return new Booking(room, guest, nights, nightlyRate, category);
    } catch (NumberFormatException e) {
        throw new IllegalArgumentException("Invalid number format in CSV line", e);
    }
} 
```

## 5. Інфраструктура
* **Система збирання:** Maven; координати проєкту `ua.lpnu.kzp:lab01:1.0.0`, Java 21 (`maven.compiler.release`), кодування UTF-8.
* **Maven Wrapper:** `mvnw` / `mvnw.cmd` і `.mvn/wrapper/`; глобальна установка Maven не потрібна.
* **Залежності:** `junit-jupiter` 5.12.2 зі скоупом `test` (підтягується Maven, у репозиторій не копіюється).
* **Плагіни:** `maven-compiler-plugin` 3.13.0, `maven-surefire-plugin` 3.5.2 (запуск тестів), `spotbugs-maven-plugin` 4.9.7.0 (мета `check` у фазі `verify`), `maven-shade-plugin` 3.6.0 (фаза `package`, головний клас `ua.lpnu.kzp.Main`).
* **Результат пакування:** виконуваний JAR `target/lab01-1.0.0.jar` (shade замінює оригінальний артефакт на JAR із залежностями).
* **Команди:**

```text
.\mvnw.cmd clean verify
java -jar target/lab01-1.0.0.jar --input data/input.csv --output out/report.txt
```

На macOS та Ubuntu замість `.\mvnw.cmd` використовується `./mvnw`.

* **CI (GitHub Actions, `.github/workflows/ci.yml`):** запускається на `push` і `pull_request` у гілки `main`/`master`. Матриця з трьох ОС: `ubuntu-latest`, `windows-latest`, `macos-latest`. Кроки: `actions/checkout@v4`; `actions/setup-java@v4` (Temurin JDK 21, кеш Maven); `chmod +x mvnw` (лише не на Windows); `./mvnw clean verify` (shell: bash); `actions/upload-artifact@v4` із файлами `target/*.jar` (назва артефакта `lab01-app-<ОС>`).
* **Версія:** `1.0.0` указана в `pom.xml`, виводиться командою `--version` і зафіксована Git-тегом `v1.0.0`.

## 11. Відповіді на контрольні питання
1. **Яку проблему розв'язує клас-сутність порівняно з рядком і паралельними змінними?**
   Клас-сутність усуває розмазану процедурну логіку перевірок і прив'язку до окремих примітивних змінних чи масивів. Він групує дані та пов'язану з ними поведінку (валідацію) в єдину логічну одиницю, що запобігає помилкам синхронізації даних та робить код значно чистішим і надійнішим.

2. **Що означають private і final у полях класу?**
   `private` обмежує область видимості поля лише межами поточного класу, приховуючи його від зовнішнього світу та реалізуючи інкапсуляцію. `final` забороняє зміну значення або посилання на поле після його первинної ініціалізації (у конструкторі), що гарантує незмінність об'єкта.

3. **Що таке інкапсуляція і яку проблему вона запобігає?**
   Це механізм об'єднання даних і методів, які ними управляють, з приховуванням внутрішньої реалізації від зовнішнього середовища. Вона запобігає проблемам неконтрольованого чи суперечливого стану об'єкта, коли зовнішній код міг би встановити невалідні або логічно хибні значення.

4. **Чому перевірку інваріантів розміщують у конструкторі?**
   Щоб унеможливити створення некоректного об'єкта в пам'яті. Якщо дані не відповідають бізнес-правилам, конструктор викидає виняток, гарантуючи, що жоден екземпляр класу не опиниться в невалідному стані.

5. **Чим Objects.requireNonNull відрізняється від isBlank?**
   `Objects.requireNonNull` перевіряє, чи не є посилання на об'єкт `null`, і викидає `NullPointerException`, якщо воно нульове. Метод `isBlank` (класу `String`) перевіряє, чи є рядок порожнім або чи складається він виключно з пробільних символів (не перевіряючи на `null`).

6. **Чому відсутність сеттерів може допомогти зберегти коректний стан?**
   Без сеттерів поля класу не можуть бути змінені ззовні після створення об'єкта (незмінність або імутабельність). Це гарантує, що стан залишається стабільним і перевіреним протягом усього життєвого циклу об'єкта.

7. **Які методи й властивості автоматично отримує record?**
   `record` автоматично генерує канонічний конструктор, публічні гетери для всіх полів (з іменами самих полів), а також методи `equals()`, `hashCode()` та `toString()`, базовані на значенні всіх компонентів.

8. **Чим record відрізняється від звичайного класу-сутності?**
   `record` є спеціальним компактним носієм незмінних даних: його поля неявно є `private final`, він не може успадковувати інші класи (але може реалізувати інтерфейси), а також має автогенеровані службові методи. Звичайний клас дозволяє змінювати стан (якщо є сеттери) та гнучкіше управляти успадкуванням.

9. **Чому record не гарантує глибоку незмінність змінного списку?**
   `record` забезпечує поверхневу незмінність (shallow immutability) — посилання на колекцію в полі record не можна змінити на інше. Проте якщо всередині record зберігається посилання на змінну структуру даних (наприклад, звичайний `List`), внутрішній вміст цього списку (елементи) все ще можна модифікувати ззовні.

10. **Для чого потрібен статичний фабричний метод fromCsv?**
    Він інкапсулює складну логіку розбору сирого рядка (форматування, поділ за розмежувачем, перетворення типів) окремо від логіки самого конструктора, забезпечуючи зручне створення об'єкта на основі зовнішніх текстових даних.

11. **Де потрібно перехоплювати помилку розбору одного рядка?**
    На рівні циклу обробки файлу (зовні від фабричного методу чи конструктора), щоб збій під час парсингу чи валідації одного окремого рядка не переривав обробку всього файлу, а дозволяв зафіксувати помилку та продовжити читати решту даних.

12. **Чому неправильний запис не можна додавати до списку до завершення перевірки?**
    Щоб сміттєві чи невалідні дані не потрапили до загального набору обчислень, що призвело б до спотворення фінальних підсумкових показників та звіту.

13. **Яке призначення toString і чому він не замінює формат CSV?**
    `toString()` створює людиночитаєме текстове представлення об'єкта (переважно для логування чи дебагу). Воно не замінює CSV, оскільки формат CSV є стандартизованим структурованим представленням табличних даних із суворим синтаксисом (роздільники, екранування), придатним для машинного читання та парсингу.

14. **Навіщо використовувати Locale.ROOT у toString і звіті?**
    Щоб гарантувати незалежність форматування числових даних (зокрема дробових чисел із крапкою) від регіональних налаштувань операційної системи користувача (де замість крапки могла б використовуватися кома).

15. **Що означає схема тесту AAA?**
    Це патерн написання юніт-тестів, що складається з трьох кроків:
    * **Arrange** (Підготовка) — створення об'єктів та ініціалізація вхідних даних.
    * **Act** (Дія) — виклик тестованого методу чи дії.
    * **Assert** (Перевірка) — порівняння отриманого результату з очікуваним за допомогою `assertEquals` тощо.

16. **Які негативні випадки потрібно перевірити для конструктора?**
    Необхідно перевірити передачу нульових значень (`null`), порожніх рядків або рядків із пробілів, від'ємних або нульових числових значень (там, де вони мають бути додатними), а також граничних чи некоректних математичних станів (наприклад, `NaN` чи `Infinity` для чисел із плаваючою комою).

17. **Як довести, що рефакторинг не змінив зовнішню поведінку попередньої роботи?**
    Пропустивши весь набір попередніх модульних тестів (які мають успішно виконуватися без модифікацій бізнес-логіки) та порівнявши результати роботи програми (консольний вивід і згенерований звіт) на ідентичних контрольних вхідних файлах.

18. **Чому тести попередньої роботи мають проходити після цієї роботи?**
    Це є головним доказом того, що зовнішній інтерфейс, правила валідації та кінцеві результати обчислень програми залишилися незмінними, тобто рефакторинг був внутрішнім і правильним.

19. **Які файли інфраструктури переносяться з попередньої роботи без повторного створення?**
    Конфігураційний файл `pom.xml`, файли Maven Wrapper (`mvnw`, `mvnw.cmd` та папка `.mvn`), а також конфігурація CI (наприклад, `.github/workflows/ci.yml`).

20. **Який рядок Вашої реалізації найкраще демонструє інкапсуляцію і чому?**
    Оголошення полів класу як `private final` разом із перевірками інваріантів безпосередньо всередині конструктора. Це найкраще демонструє інкапсуляцію, оскільки стан повністю захищений від зовнішніх модифікацій і жоден об'єкт не може бути створеним у некоректному вигляді.
