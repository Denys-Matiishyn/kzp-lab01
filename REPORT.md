## 4. Базовий тип
`Booking` — **абстрактний клас** (`public abstract sealed class Booking permits StandardBooking, PremiumBooking`).

* **Спільні поля:** `room`, `guest`, `nights`, `nightlyRate`, `category` (усі `private final`) і `kind` (`RoomKind`, виводиться з `category`).
* **Інваріанти (в одному місці, не дублюються в підтипах):** `guest` і `category` не порожні; `room > 0`; `nights > 0`; `nightlyRate` додатне й скінченне. Тексти повідомлень збережено з ЛР № 2, тому вивід відхилених рядків не змінився.
* **Абстрактні методи:** `double stayCost()` (поліморфна операція варіанта) і `String tierLabel()`.
* **Фінальні методи:** гетери, `getRevenue()`, `toString()` (формат рядка збережено).
* **Чому абстрактний клас, а не інтерфейс:** підтипи мають спільний *стан* і спільну *валідацію*; інтерфейс не може містити поля екземпляра й конструктор. Інтерфейс доречний, коли потрібен лише контракт можливості.
* **Чому спадкування, а не композиція:** `StandardBooking` і `PremiumBooking` справді є різновидом бронювання (відношення «is-a»), мають однакові дані й однаковий спосіб використання. Композиція (`has-a`) була б доречна, якби, наприклад, бронювання лише *містило* окремий об'єкт «тарифний план»; тут це дало б зайвий шар без користі.
* **Конструктор і SpotBugs:** публічний (protected) конструктор делегує приватному `this(validate…(…), …, true)`. Перевірки виконуються під час обчислення аргументів, а приватний конструктор лише присвоює поля. Так не виникає «часткового» об'єкта в конструкторі, що кидає виняток (попередження `CT_CONSTRUCTOR_THROW` для нефінального класу). Порядок аргументів збігається з порядком перевірок ЛР № 2.

```java
protected Booking(int room, String guest, int nights, double nightlyRate, String category) {
    this(validateGuest(guest), validateCategory(category), validateRoom(room),
            validateNights(nights), validateRate(nightlyRate), true);
}
```

## 5. Підтипи
| | `StandardBooking` | `PremiumBooking` |
| :-- | :-- | :-- |
| Категорії | Economy, Standard, Deluxe, Business, невідомі (`OTHER`) | Suite, Presidential, Penthouse |
| Власне поле | `longStayDiscount` (за замовчуванням 5 %) | `serviceCharge` (за замовчуванням 10 %) |
| Власна перевірка | знижка скінченна й у [0; 1) | збір скінченний і в [0; 1] |
| `stayCost()` | `nights × rate`; від 7 ночей мінус знижка | `nights × rate × (1 + serviceCharge)` |
| `tierLabel()` | `"Standard"` | `"Premium"` |

Конструктор підтипу спочатку викликає `super(...)` (спільні перевірки), потім перевіряє власне поле. Обидва класи `final` й оголошені в `permits`. Для підтипів перевизначено `equals`/`hashCode`, бо додано поле, що впливає на поведінку.

```java
// StandardBooking
@Override
public double stayCost() {
    if (getNights() >= LONG_STAY_NIGHTS) {
        return getRevenue() * (1.0 - longStayDiscount);
    }
    return getRevenue();
}

// PremiumBooking
@Override
public double stayCost() {
    return getRevenue() * (1.0 + serviceCharge);
}
```

Формат CSV не змінювався, тому власні поля підтипів мають значення за замовчуванням (додаткові конструктори з шостим параметром використовуються в тестах і доступні для розширення).

## 6. enum
`RoomKind`: `ECONOMY`, `STANDARD`, `DELUXE`, `BUSINESS`, `SUITE`, `PRESIDENTIAL`, `PENTHOUSE`, `OTHER`. Поля: назва в CSV, український підпис (`label()`), ознака преміальності (`isPremium()`). Метод `RoomKind.fromCategory(String)` не залежить від регістру й пробілів.

Значення `OTHER` потрібне для **сумісності**: ЛР № 2 приймала будь-яку непорожню категорію, тож рядок із категорією, якої немає в переліку, має лишатися коректним. Значення `enum` порівнюються через `==`; `switch` за категорією в обробці немає, категорія використовується лише у фабриці `Booking.create`, щоб обрати підтип.

## 7. equals і hashCode
* **Критерій рівності:** однаковий клас (підтип) і однакові `room`, `guest`, `nights`, `nightlyRate` (через `Double.compare`), `category`; підтипи додатково порівнюють своє поле (`longStayDiscount` або `serviceCharge`).
* **Чому `getClass()`, а не `instanceof`:** об'єкти різних підтипів із однаковими даними мають різну поведінку (`stayCost()`), тому не вважаються рівними й рівність симетрична.
* **hashCode:** `Objects.hash(getClass(), room, guest, nights, nightlyRate, category)`, у підтипах додається своє поле через `Objects.hash(super.hashCode(), …)`.
* **Незмінність:** усі поля `private final`, тому об'єкт безпечно використовувати як ключ `HashMap`.
* **Перевірка в колекціях:** тести `hashSetDoesNotDuplicateEqualBookings` (4 вставки → 2 елементи) і `hashMapFindsValueByLogicallyEqualKey`; у консольному блоці програми `Unique bookings` рахується через `HashSet`.

## 8. Поліморфізм
`Main.buildPolymorphicDetails(List<? extends Booking>)` отримує список спільного типу й для кожного елемента викликає `b.stayCost()` та `b.tierLabel()`. Метод не знає конкретних класів:

```java
for (Booking b : bookings) {
    totalStayCost += b.stayCost();
    perTier.merge(b.tierLabel(), 1, Integer::sum);
}
```

* **Поліморфний метод:** `Booking.stayCost()`.
* **Чому немає центрального `if`/`switch`:** різницю правил вартості реалізовано в підтипах. Додавання нового підтипу (наприклад, `GroupBooking`) потребує нового класу й запису у фабриці, а код звіту не змінюється. У `src/main` немає жодного `instanceof`.
* **Єдине розгалуження за категорією** — у фабриці створення `Booking.create`; це вибір підтипу під час створення, а не обробка.
* **Завдання із зірочкою:** `BookingDescriber.describeRule` використовує `switch` зі зіставленням зі зразком над запечатаною ієрархією **без `default`**. Якщо додати третій дозволений підтип у `permits` і не оновити `switch`, компіляція завершиться помилкою «the switch expression does not cover all possible input values». Вартість тут не дублюється, `switch` лише формує текстовий опис правила й не використовується в обчисленні показників.

## 14. Відповіді на контрольні питання
1. **Яку спільну проблему розв'язує базовий тип?** Він збирає спільні поля й правила кількох сутностей в одному місці, тому їх не доводиться дублювати, а код обробки працює з одним типом. У нас це `Booking` зі спільною валідацією.
2. **Чим відрізняються `extends` і `implements`?** `extends` успадковує клас (стан і реалізацію), і клас може мати лише одного предка. `implements` підключає інтерфейс-контракт, їх можна реалізувати кілька.
3. **Навіщо базовий клас може бути `abstract`?** Щоб не можна було створити «загальне» бронювання без конкретного правила вартості, а підтипи зобов'язувались реалізувати абстрактні методи.
4. **Яку роль виконує `super(...)`?** Викликає конструктор базового класу, який ініціалізує й перевіряє спільну частину об'єкта до того, як підтип встановить власні поля.
5. **Що перевіряє `@Override`?** Компілятор перевіряє, що метод справді перевизначає метод предка з такою самою сигнатурою; одруківка в імені дасть помилку компіляції.
6. **Що таке поліморфізм і як він усуває розгалуження за типом?** Змінна базового типу може посилатися на об'єкт підтипу, а під час виконання викликається реалізація фактичного класу. Відмінність поведінки живе в підтипі, тому `if (x instanceof …)` не потрібен.
7. **Коли інтерфейс, а коли абстрактний клас?** Абстрактний клас — коли є спільний стан і готова частина реалізації (як у нас). Інтерфейс — коли описується лише можливість, яку можуть мати несхожі класи.
8. **Що означає «є різновидом» і чим відрізняється від композиції?** `is-a` — підтип можна використовувати всюди, де очікується базовий тип. Композиція (`has-a`) — один об'єкт лише містить інший як поле й не наслідує його інтерфейс.
9. **Для чого `enum` із полями та методами?** Фіксована множина значень із даними й поведінкою: `RoomKind` зберігає підпис і ознаку преміальності, а недопустимих категорій немає.
10. **Чому значення `enum` порівнюють через `==`?** Кожна константа існує в єдиному екземплярі, тож порівняння посилань еквівалентне порівнянню значень і не кидає `NullPointerException`.
11. **Які правила для `equals`/`hashCode`?** `equals` рефлексивний, симетричний, транзитивний, узгоджений і `x.equals(null) == false`; якщо `a.equals(b)`, то `hashCode` однаковий.
12. **Чому змінне поле небезпечне для ключа `HashMap`?** Після зміни поля змінюється хеш-код, і об'єкт опиняється не в тому кошику: його вже не знайти за ключем. Тому поля `Booking` — `final`.
13. **Чому об'єкти різних підтипів можуть бути нерівними за однакової назви?** Вони мають різну поведінку; перевірка `getClass()` гарантує, що `StandardBooking` і `PremiumBooking` з однаковими даними не зливаються в `HashSet`.
14. **Як поліморфна колекція обробляє різні підтипи?** Цикл за `List<Booking>` викликає однакові методи; JVM сама обирає реалізацію за фактичним класом елемента.
15. **Які тести доводять різну поведінку підтипів?** `subtypesCalculateCostDifferentlyForSameInput`, `standardGivesDiscountOnlyForLongStay`, `premiumAddsServiceCharge`.
16. **Які тести доводять коректність рівності в `HashSet`?** `hashSetDoesNotDuplicateEqualBookings`, `equalObjectsHaveSameHashCode`, `differentSubtypesWithSameDataAreNotEqual`, `hashMapFindsValueByLogicallyEqualKey`.
17. **Що контролює `sealed` і навіщо `permits`?** Обмежує перелік дозволених прямих підтипів. Завдяки цьому компілятор перевіряє вичерпність `switch` без `default`.
18. **Чому `switch` за підтипами не повинен дублювати поліморфні методи?** Інакше логіка розмножується: новий підтип доведеться додавати і в клас, і в кожен `switch`. У `BookingDescriber` `switch` лише описує правило текстом, а обчислення лишається в `stayCost()`.
19. **Які попередні тести та результати потрібно зберегти?** Усі 9 тестів ЛР № 1–2 і контрольний звіт (`baseline/report-lab01.txt`). Єдине виправлення — виклик фабрики замість `new Booking` у `BookingTest`.
20. **Яке рішення найкраще демонструє перевагу поліморфізму?** Цикл у `buildPolymorphicDetails`: він викликає `stayCost()` для будь-якого підтипу й не змінюється при додаванні нових.

## 15. Висновки
У роботі клас-сутність `Booking` перетворено на запечатану ієрархію з абстрактним базовим класом і двома підтипами з різним правилом вартості проживання, категорію описано `enum RoomKind`, реалізовано узгоджені `equals`/`hashCode` та перевірено їх у `HashSet` і `HashMap`. Обробка різнорідних об'єктів виконується через спільний тип без `instanceof` і без `switch` за підтипом. Файл звіту збігається з еталоном ЛР № 1, усі попередні тести проходять, загальна кількість тестів зросла до 40. Ця модель стає основою для наступної роботи, де колекції бронювань оброблятимуться потоками та складеними запитами.
